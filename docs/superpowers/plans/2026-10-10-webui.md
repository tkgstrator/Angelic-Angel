# Personal operations WebUI implementation plan

> **For agentic workers:** Use the authorized Claude Code MCP implementation
> workers for independent backend and frontend tasks. Codex owns integration,
> browser verification, commits and merge. Execute task by task with meaningful
> failing tests before implementation.

**Goal:** Deliver the approved three-screen React/Vite WebUI backed by Rust,
included in the lightweight image and validated in CI before merge.

**Architecture:** One Rust service owns configuration and receiver lifecycle.
Authenticated JSON DTOs feed a static React client served from the same process.
Configuration locks, atomic writes and receiver stop/join prevent stale updates.

**Tech stack:** Rust 1.99.0, Tokio, Axum; React, TypeScript, Vite, Vitest and
Testing Library; Node 22 for CI/build only; existing Distroless Debian 12 runtime.

**Spec:** `docs/superpowers/specs/2026-10-10-webui-design.md`

## Global constraints

- Three main screens: settings, registration/unregistration, receiver status.
- CLI compatibility; Rust 1.99.0; Node 22 compatible locked frontend dependencies.
- Single-account personal tool, Compose loopback publication, Bearer-authenticated
  APIs, no saved cookies/private keys/raw vendor errors in responses.
- Atomic mode-0600 config persistence, exclusive lifetime ownership, serialized
  mutations and joined receiver task before writing.
- Environment webhook precedence, old TOML compatibility, honest runtime state.
- Only compiled web assets and stripped Rust executable in the non-root runtime.
- No worker commits; Codex uses the native identity/message/push checker.

## Review focus

- Simultaneous re-registration and settings edits must never restore stale keys.
- Remote timeout/failure must preserve usable registration and stop duplicate listeners.
- Empty, invalid or partially updated secrets must neither erase cookies nor leak them.
- Old environment-based installations must retain their webhook behavior.
- Unauthorized requests, stale tokens, API misses and SPA routes must remain distinct.

## Task 1: Rust service, HTTP contract and receiver lifecycle

**Owner:** Claude backend worker; no edits in `web/`, Docker, workflows or docs.
**Files:** `Cargo.toml`, `Cargo.lock`, `src/main.rs`, `src/cli.rs`, `src/config.rs`,
`src/listener.rs`, small new focused `src/web/` or service modules and backend tests.
Small provider changes only where lifecycle/error redaction needs them.
**Interfaces:** Preserve `listener::listen(registration, config_path)` for CLI.
Produce the exact HTTP contract in the spec, `serve --bind ADDRESS` and `web-token`.
`WEBUI_ASSETS_DIR` selects assets, default `web/dist`; container integration sets
`/usr/share/angelic-angel/web`. Rust API compilation does not require built assets.

## Task 2: React client and meaningful component tests

**Owner:** Claude frontend worker; owns only `web/`.
**Files:** `web/package.json`, lockfile, Vite/TS/lint/test configuration, focused
`web/src/` components, styles and tests.
**Interfaces:** Consume the spec's exact HTTP contract with a centralized typed
client and stable error handling. Use hash navigation and `/api` development
proxy, with no mocked production endpoints. `npm run typecheck`, `lint`, `test`
and `build` must exist, work on Node 22 and use the committed lockfile.

- [ ] Write and run failing tests for login success/401, session token handling,
  logout and sanitized error presentation.
- [ ] Implement the auth gate, typed API client, navigation and responsive shell.
- [ ] Write and run failing settings tests: blank saved secrets, required first

- [ ] Implement the settings screen with accessible labels and form feedback.
- [ ] Write and run failing registration tests for registered/unregistered states,

- [ ] Implement registration/unregistration without duplicating provider logic.
